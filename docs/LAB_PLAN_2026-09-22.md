## The three levers

### Coverage — `hotspot_speed`: how fast the target moves

Lloyd/Cortés coverage assumes a **static density**. Ours already moves (0.3
rad/s), which is why the fleet never quite settles. Speeding it up moves further
from the theorem without touching the controller at all.

| | |
|---|---|
| Baseline | 0.3 rad/s (flown 16 Sep as c2, k·τ 0.67) |
| Ladder | 0.6, then 0.9 rad/s |
| Measure | H above optimum, `cdist` per drone, design-gap (figure 2) |
| Predict | H rises smoothly; design-gap grows roughly as `speed × 0.28 s` |

**Is this just the speed ladder again?** No, and the distinction matters for the
writeup. The speed ladder changed the **controller** (gains), which changed
`k·τ` and therefore the stability margin. This changes the **problem**, not the
controller: `kp` and `kd` are untouched, so `k·τ` stays at 0.67 and the delay
margin is exactly as before. What changes is how non-stationary the task is.

**Could it still oscillate?** Not the delay limit cycle — that is governed by
k·τ, which does not move. There is one indirect route: chasing a faster target
means larger position errors, so `kp · error` grows, and if the command starts
hitting the 3.5 m/s² clamp then saturation lowers the effective gain and can
trip the limit cycle. **Watch the clipped-ticks number after each run.** If it
leaves 0%, stop climbing.

Two hard limits on how far this can go: `crazyflie_node` caps the setpoint speed
at 0.7 m/s, and the drones' own speed scales roughly with hotspot speed (0.16
m/s at 0.3 rad/s). 0.9 rad/s should give ~0.5 m/s — close enough to the cap that
1.2 rad/s is not worth attempting.

**The quantitative prediction worth testing:** the drone is always τ behind, so
distance-behind ≈ speed × 0.28 s. At 0.16 m/s that is 4.5 cm; at 0.5 m/s it is
14 cm. If the design-gap grows linearly with speed at that slope, the delay
explains the whole degradation. If it grows faster, something else is also
breaking.

### Flocking — `sense_range`: how far each agent can see

Olfati-Saber's proof needs the neighbour graph to **stay connected**. That is
the assumption a real deployment loses first (limited radio range, occlusion),
and it is the one our lever attacks.

| | |
|---|---|
| Baseline | `sense_range` 0.84 with `spacing` 0.70, i.e. r/d = 1.2 (flown as s2) |
| Ladder | 0.78 (r/d 1.11), then 0.73 (r/d 1.04) |
| Measure | `connected` and `n_edges` columns, lattice error, `d_min` |
| Predict | **corrected 22 Sep:** simulation says the graph never fragments at any legal rung — the flock compresses instead (sides 0.584 → 0.569 → 0.550) and stays 100% connected. So the test is whether *hardware* can hold a marginal edge: any reading below 100% connected is a pure physical-layer effect. |

**Why shrinking the range breaks things — it does not move the drones.**
`sense_range` is how far an agent can *see*, not how far apart they sit. Spacing
is set separately (`spacing` 0.70) and the settled geometry is fixed: sides
0.586 m, short diagonal 0.700 m, long diagonal 0.939 m. With r = 0.84 the long
diagonal pair **already cannot see each other** (0.939 > 0.84), so the flock
runs on 5 of 6 possible edges. Shrink r to 0.73 and the 0.700 m diagonal pair
falls out too, leaving only the four sides — a bare cycle, with no margin. As
the lattice breathes, that pair flickers in and out of range, which is exactly
the intermittent connectivity the theorem assumes away.

Note the literature's own guidance (quoted in `flocking.py`) is r/d between 1.2
and 1.5. We are *already at the bottom of that band*. Today walks below it.

**Simulated k·τ falls as the range shrinks** — 0.63 → 0.55 → 0.51 — because
fewer visible neighbours means a smaller Σ of bump weights. Connectivity
degrades while the delay margin *improves*. Benign, but it means these rungs
cannot be read as oscillation tests.

**Two constraints.** `flocking.py` refuses to configure with `sense_range <=
spacing`, so 0.73 is near the floor unless spacing also drops. And fewer
neighbours means a smaller Σ of bump weights, so **k falls** — the delay margin
improves as connectivity degrades. That is a confound but a benign one: it moves
away from oscillation, not toward it, and the analysis recomputes k per drone
from the flight data anyway.

### Trochoidal — gain detuning: the poles must sit exactly on the axis

The paper places two eigenvalue pairs **exactly on the imaginary axis**. That is
marginal stability: nothing restores the poles if they drift off, so the pattern
grows or decays exponentially instead of persisting. It is the paper's most
obviously-untrue-on-hardware assumption, and it is quantitatively predictable.

| | |
|---|---|
| Baseline | r2's designed gains: α 0.2026, β 2.0, κ 0.0364 (size held ×1.00/lap) |
| Ladder | α +5% (shrinks), then α −2% (grows) |
| Measure | size change per fast lap — already reported by the ladder script |
| Predict | see the table below |

Computed from the fig-4 Laplacian with r2's gains (fast lap 57.1 s):

| detune | max Re(pole) | size per lap | size after 180 s |
|---|---|---|---|
| as designed | ~0 | 1.00 | 1.00 |
| α +2% | −1.9e−3 | 0.898 | 0.71 |
| α −2% | +2.1e−3 | 1.129 | 1.47 |
| α +5% | −4.9e−3 | 0.756 | 0.41 |
| α −5% | +5.2e−3 | 1.342 | 2.53 |
| κ +5% | +5.4e−3 | 1.362 | 2.65 |

**Have we not already done this by changing β?** No — and this is the important
distinction. The speed ladder changed α, β and κ **together**, by exactly the
factors (c², c, c²) that keep the design self-consistent: the two pole pairs
stayed *on* the imaginary axis and merely moved along it, which is why r2 held
its size at ×1.00 per lap for 185 s. Detuning changes **one** gain so the design
is no longer self-consistent and the poles leave the axis. We have never flown a
deliberately mis-designed set. Every trochoidal flight so far used correctly
designed gains.

**Why it is worth flying:** if a 2% gain error visibly changes the pattern size
over three minutes, the finding is *"this method requires gain accuracy better
than X% to hold its size over a flight"* — a concrete, practical statement about
the paper's applicability, which is exactly what this project is for.

**Safety:** fly the shrinking direction (α +5%) first — it is unconditionally
safe. The growing direction reaches ×1.47 in 180 s at α −2%, which stays inside
the geofence; do **not** fly α −5% for a full 180 s (×2.53 would reach the edge).
